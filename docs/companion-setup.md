# Private model-assisted companion — development setup

This is a single-owner prototype, not public multi-tenant authentication. The old public quote API is unchanged; the new service is isolated and binds only to loopback. It sends selected excerpts to a configured model provider. The service itself does not persist passages or chat or log their content. Provider and reverse-proxy policies still apply. Do not expose the HTTP port directly, log authorization headers or bodies, or configure public CORS.

1. In backend, run npm ci. Add the variables from .env.companion.example to backend/.env. Generate an access token using openssl rand -hex 32. Choose a provider and model supporting an HTTPS chat-completions-compatible endpoint, JSON-object response format and max_tokens. The full endpoint and key must be configured server-side. Do not use a ChatGPT subscription as an API key.
2. Run npm run test:companion and npm run companion from backend. Node 22+ required. Expose only the /v1/reading POST route behind a trusted HTTPS reverse proxy that forwards to 127.0.0.1:5050; configure request size/time limits and avoid request-body logging. Use a separate origin, valid certificate and a private high-entropy access token.
3. Open Discover > reading companion on the mobile app. Enter the HTTPS origin and token (not model key). Select up to ten actual passages, optionally allow their personal notes, enter a question or request a connection, and explicitly consent to each request. Inspect source excerpts. Follow up in the same screen; six recent messages are sent as context. Changing source selection, note sharing or server clears the conversation. Closing the screen loses the conversation and token. For exactly two cited passages from different books, the reader may select their own relationship and save a reflection.
4. Test no token, wrong token, oversized request, provider failure, no evidence, fabricated ID/quotation, one-book connection, notes excluded, and an actual two-book comparison on the phone.

Limits: manually selected context rather than whole-library semantic retrieval; no embeddings, voice, automatic connection feed, cross-session history or multi-user account integration yet. Exact source substring validation catches fabricated evidence but cannot prove every interpretation is correct. The provider may still produce poor inferences; the UI labels those as AI interpretation and never automatically saves them as the reader's beliefs. The current pair-saving UI supports exactly two cited passages; multi-book answers can be read and discussed but cannot be saved as a single thread yet. No configured provider, TLS deployment or phone test has been performed.

## Semantic retrieval (slice 04)

Optional embedding configuration: set COMPANION_EMBEDDING_URL (full fixed HTTPS embeddings endpoint), COMPANION_EMBEDDING_MODEL and COMPANION_EMBEDDING_KEY on the server. Provider must support OpenAI-compatible indexed embedding responses with finite equal-dimension vectors. All three settings are required together; missing settings disable retrieval without disabling manual discussion. Extend the HTTPS reverse proxy allowlist to POST /v1/retrieve; keep the loopback bind, token, rate limit and no-content-logging policy. Restart the service.

From Today or Discover > companion, enter a question (optional in connect mode), choose whether to include notes, and open Find evidence automatically. The phone scans all eligible local passages, prepares up to 24 excerpts (1800 characters and optional 800-character notes each), shows exactly what will leave the phone, and sends them only after the explicit search action. No conversation history or saved reflection text is sent in this retrieval request. Favorites, reading status, earlier saved reflections as a local priority signal, and previous pair decisions influence candidate selection. The server uses cosine similarity and book/semantic diversity to return at most six IDs, keeping the anchor and another book for connections. Review/edit full selected passages before separately consenting to the existing model interpretation request. Retrieval has no persistent embedding index and may miss connections outside the bounded shortlist; it is not exhaustive whole-library vector search. Embeddings are ephemeral, so repeat calls incur provider cost. No provider configured or live request tested.
